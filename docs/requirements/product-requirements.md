# DocWeave Product Requirements

**Version:** 0.1
**Baseline approved:** 2026-07-21
**Implementation status:** Not started
**Product surfaces:** PySide6 desktop application and complete cloud application

## 1. Product vision

DocWeave helps legal, procurement, compliance, and document-control teams turn
large, poorly named PDF collections into an organized, explainable, and
reversible workspace.

The product discovers documents, reads and classifies them, proposes meaningful
names and destinations, identifies related documents, and executes approved
copy or move operations. CockroachDB provides durable memory for document
identity, analysis, user decisions, operation history, relationships, and agent
activity. Amazon Web Services provides the complete cloud runtime and judged
application.

DocWeave reduces repetitive manual work without removing human authority. An
agent may recommend a consequential filesystem operation; a person decides
whether it is executed.

## 2. Problem statement

Business teams may receive folders containing hundreds or thousands of
invoices, purchase proposals, contracts, tender documents, appendices, and
supporting records. Filenames are often generated by scanners or external
systems and provide little useful information. People must open files one by
one, infer their purpose, rename them, create folders, and preserve enough
context for later review.

The process is slow and difficult to supervise. Mistakes can separate related
documents, overwrite useful files, obscure responsibility, or make the original
state impossible to reconstruct. Existing bulk-renaming tools generally do not
understand document content, explain uncertainty, learn from reviewer
corrections, or maintain a durable and auditable memory.

## 3. Target users

### 3.1 Operator

An operator imports folders, reviews proposals, corrects metadata, and prepares
actions. Operators are not expected to understand databases, prompts, or cloud
infrastructure.

### 3.2 Reviewer or project manager

A reviewer monitors quality, prioritizes uncertain results, approves sensitive
or bulk actions, inspects team activity, and restores individual files or
batches when necessary.

### 3.3 Administrator

An administrator manages workspaces, members, roles, policies, supported file
limits, classification taxonomies, and operational settings.

## 4. Product principles

1. **Preview before mutation.** No copy, move, rename, restore, or folder
   creation occurs without a visible plan and authorization.
2. **Identity survives location changes.** A document remains recognizable
   after renaming, moving, copying, rescanning, or application restart.
3. **Every material action is reversible where technically possible.** A
   failed reversal is explicit and actionable; it is never reported as a
   success.
4. **Uncertainty drives review.** Confidence helps people prioritize work but
   never replaces evidence or human judgment.
5. **History is append-only.** A correction or restore creates another event;
   it does not erase the original action.
6. **Intelligence is genuine and evaluated.** Model behavior is not replaced
   with canned classifications or hidden demonstration data.
7. **The cloud product is complete.** The judged deployment uses the real
   agents, memory, workflows, review controls, and operation history.
8. **Complexity stays behind the interface.** Users operate through clear
   actions and plain-language explanations, not direct database commands.

## 5. Approved capacity envelope

The capacity envelope distinguishes discovery from active processing so that a
large folder remains manageable without requiring one unbounded agent run.

| Measure | Approved MVP target |
| --- | ---: |
| Files discoverable in one source folder | 10,000 |
| Files actively managed in one project | 5,000 |
| Maximum documents in one processing batch | 1,000 |
| Primary demonstration corpus | Approximately 300 |
| Scale and resume test | Up to 10,000 files |

The limits are configurable policy values, not assumptions embedded throughout
the implementation. Reaching a limit produces a clear message and preserves
all completed work.

## 6. Functional requirements

### 6.1 Workspace and discovery

- **FR-001:** A user shall be able to create or open a document workspace.
- **FR-002:** The desktop application shall allow an authorized local folder to
  be selected without granting access outside the selected roots.
- **FR-003:** The cloud application shall provide a functionally complete cloud
  document workspace rather than a reduced or simulated demonstration.
- **FR-004:** A scan shall discover supported PDF files recursively and report
  supported, unsupported, unreadable, missing, and duplicate candidates.
- **FR-005:** A repeated scan shall identify new, unchanged, changed, moved,
  missing, completed, and interrupted files without automatically reprocessing
  completed content.
- **FR-006:** Scanning and indexing shall remain responsive at the approved
  10,000-file discovery target.

### 6.2 Stable document identity

- **FR-007:** Every logical document shall receive a stable internal identity
  independent of filename and path.
- **FR-008:** Every physical file instance shall have its own identity, role,
  location, and lifecycle so an original and an organized copy are not
  confused.
- **FR-009:** The product shall record content fingerprints and relevant file
  metadata to support identity checks and external-change detection.
- **FR-010:** A content change shall create a distinguishable document version
  or review condition rather than silently replacing recorded evidence.

### 6.3 Analysis and classification

- **FR-011:** The system shall extract usable content and metadata from each
  supported PDF and explicitly report extraction limitations.
- **FR-012:** Agent-driven analysis shall propose a document class, meaningful
  filename, destination, and related-document links where supported by
  evidence.
- **FR-013:** Every classification result shall record a raw confidence,
  calibrated confidence, explanation, evidence references, model identity,
  model version, analysis configuration, and timestamp.
- **FR-014:** Reanalysis shall create a new result linked to its predecessor;
  prior classifications shall remain available.
- **FR-015:** A human correction shall record the proposed value, final value,
  reviewer, time, and optional reason.
- **FR-016:** Approved corrections may inform later recommendations through
  controlled preference memory without rewriting historical results.
- **FR-017:** Related-document proposals shall state the relationship type,
  supporting evidence, confidence, and review status.

### 6.4 Review and prioritization

- **FR-018:** Users shall be able to sort confidence in ascending or descending
  order without relying on database storage order.
- **FR-019:** Users shall be able to filter results by confidence range,
  classification, review state, batch, user, date, action type, and error state.
- **FR-020:** The review interface shall display the PDF, current metadata,
  proposed classification, proposed path, proposed filename, explanation, and
  evidence together.
- **FR-021:** A reviewer shall be able to approve, reject, or edit a single
  proposal or a selected group.
- **FR-022:** The system shall support configurable confidence bands and a
  low-confidence review queue.
- **FR-023:** The system shall support random or policy-based sampling of
  high-confidence results to detect systematic overconfidence.
- **FR-024:** A batch preview shall summarize file counts, actions, folders,
  conflicts, warnings, estimated processing time, and estimated cloud cost
  before approval.

### 6.5 Copy, move, and restore

- **FR-025:** In move mode, an approved operation shall rename or relocate the
  existing file and preserve its complete prior state in persistent history.
- **FR-026:** In copy mode, an approved operation shall preserve the source and
  create a separately tracked organized copy.
- **FR-027:** The system shall never overwrite an unrelated existing file
  automatically.
- **FR-028:** Missing destination or restore directories may be recreated only
  within authorized roots and as part of an approved plan.
- **FR-029:** A user shall be able to restore the immediately previous state or
  the original discovered state of a moved file.
- **FR-030:** Reverting a copy operation shall preserve the original and place
  the DocWeave-created copy in the operating system's recoverable trash where
  supported.
- **FR-031:** A reviewer shall be able to restore one file, a selection, or a
  complete identified batch.
- **FR-032:** Restore shall perform current-state, identity, permission, and
  collision checks before changing a file.
- **FR-033:** Partial success shall be represented per file; one failure shall
  not make the status of an entire batch ambiguous.
- **FR-034:** Interrupted operations shall be resumable from persistent
  checkpoints and safe against duplicate execution.

### 6.6 Team control and activity history

- **FR-035:** Every consequential action shall identify the initiating user,
  approving user where applicable, responsible agent, timestamps, prior state,
  intended state, actual result, and error details.
- **FR-036:** The Activity History shall support document, batch, user, agent,
  action, status, and date filtering.
- **FR-037:** Restores, corrections, and retries shall append events rather than
  delete or rewrite earlier events.
- **FR-038:** Role-based authorization shall distinguish Operator, Reviewer or
  Project Manager, and Administrator capabilities.
- **FR-039:** Approval policy shall be configurable so high-impact batches may
  require a reviewer other than the initiating operator.
- **FR-040:** A project manager shall be able to inspect completed and pending
  work without direct database access.

### 6.7 Persistent agentic memory

- **FR-041:** CockroachDB shall persist operational memory: workspaces,
  documents, physical instances, versions, batches, proposals, executions, and
  restores.
- **FR-042:** CockroachDB shall persist semantic memory: extracted content,
  classifications, embeddings, evidence, and document relationships.
- **FR-043:** CockroachDB shall persist episodic memory: agent runs, tool use,
  handoffs, checkpoints, failures, and outcomes.
- **FR-044:** CockroachDB shall persist controlled preference memory derived
  from explicit user choices and corrections with provenance and revocation.
- **FR-045:** Memory retrieval shall respect workspace and user authorization;
  retrieved document content shall never become trusted agent instruction.
- **FR-046:** The application shall visibly demonstrate how persistent memory
  changes or resumes a real workflow.

### 6.8 Product parity

- **FR-047:** Desktop and cloud surfaces shall use the same production agent
  workflows, persistent memory, classification logic, confidence model, review
  policy, and audit semantics.
- **FR-048:** The desktop surface shall operate on user-authorized local
  filesystem roots.
- **FR-049:** The cloud surface shall operate on a real cloud-backed document
  workspace and expose the complete judged workflow.
- **FR-050:** Differences caused by storage medium or operating-system
  capability shall be explicit, tested, and documented; they shall not hide a
  reduced intelligent path.

### 6.9 Memory and database stewardship agent

- **FR-051:** The multi-agent system shall include an explicitly bounded memory
  and database stewardship responsibility for retrieving relevant memory,
  preserving provenance, detecting inconsistent or incomplete records, and
  reporting operational anomalies.
- **FR-052:** The stewardship agent may propose database maintenance,
  optimization, or schema actions, but it shall not execute schema changes,
  destructive statements, privilege changes, or unrestricted free-form queries
  without deterministic authorization and the required human approval.
- **FR-053:** Database constraints, transactions, access control, idempotency,
  and audit integrity shall be enforced by deterministic database and
  application controls rather than delegated to language-model judgment.
- **FR-054:** Every stewardship-agent read, proposal, diagnostic action, and
  authorized mutation shall be scoped, observable, and attributable in the
  agent and audit history.

### 6.10 Relational domain data

- **FR-055:** Important document, operational, and approved business data shall
  be persisted in typed relational CockroachDB tables rather than hidden in
  opaque application objects.
- **FR-056:** The initial relational domain shall represent projects,
  suppliers, tenders, contracts, purchase orders, invoices, payments, and their
  links to source documents where required by the approved workflow.
- **FR-057:** Proposed extracted facts shall retain typed values, confidence,
  evidence, model provenance, review state, and history separately from
  human-approved canonical facts.
- **FR-058:** JSON may retain minimized raw technical evidence where approved,
  but it shall not be the sole authoritative representation of classification,
  canonical facts, file operations, relationships, or audit history.
- **FR-059:** The demonstration dataset shall use fictional values and
  internally consistent document dossiers inspired only by general real-world
  field categories and relationships.
- **FR-060:** Private reference records, exact filenames, company identifiers,
  tax identifiers, payment references, and amounts shall not be copied into the
  repository, prompts, generated corpus, or demonstration.

## 7. Non-functional requirements

### 7.1 Usability and accessibility

- **NFR-001:** Normal workflows shall require no direct Structured Query
  Language, prompt editing, command-line use, or cloud-console access.
- **NFR-002:** Long operations shall run in the background with progress,
  cancellation where safe, checkpoint status, and understandable recovery
  guidance.
- **NFR-003:** Destructive or high-volume actions shall use clear language,
  consequence summaries, and explicit confirmation.
- **NFR-004:** Desktop and web interfaces shall meet the approved accessibility
  baseline in the Quality and Security Charter.
- **NFR-005:** Tables shall remain navigable and responsive at the 5,000-row
  active-project target through pagination or data virtualization.

### 7.2 Reliability and integrity

- **NFR-006:** Operation execution shall be idempotent: replaying the same
  authorized command shall not create an unintended duplicate effect.
- **NFR-007:** A process, network, or model failure shall not erase completed
  state or incorrectly mark unfinished work as successful.
- **NFR-008:** File and database state divergence shall be detectable,
  reportable, and recoverable through a defined reconciliation workflow.
- **NFR-009:** Audit history shall be tamper-evident and retained according to
  an approved policy.
- **NFR-010:** Original content shall never be overwritten as an implicit side
  effect of classification or analysis.

### 7.3 Performance

- **NFR-011:** Folder discovery shall expose progressive results rather than
  freeze the interface until the full scan completes.
- **NFR-012:** Sorting or filtering 5,000 indexed results shall return an
  interactive first view within two seconds under the reference test setup.
- **NFR-013:** The application shall bound parallel model and file operations
  to protect cost, rate limits, local resources, and service stability.
- **NFR-014:** Exact analysis latency targets shall be established after a
  representative model benchmark and approved before implementation.

### 7.4 Security and privacy

- **NFR-015:** Access shall follow least privilege and workspace isolation.
- **NFR-016:** Sensitive file content, paths, and extracted data shall be
  minimized in logs and protected in transit and at rest.
- **NFR-017:** Only explicitly authorized roots or cloud workspaces may be read
  or changed.
- **NFR-018:** Untrusted filenames, paths, PDF content, and model output shall be
  validated before use in a filesystem or tool operation.
- **NFR-019:** Demonstration and automated evaluation shall use authorized,
  synthetic, or safely licensed documents rather than confidential company
  records.

### 7.5 Cost and operations

- **NFR-020:** Total AWS expenditure shall remain within the user-approved
  80 USD project ceiling unless a new limit is explicitly approved. Available
  promotional credits do not increase this authorization.
- **NFR-021:** Paid workloads shall not begin before budgets, alerts, usage
  limits, and shutdown guidance are established.
- **NFR-022:** Per-batch estimates and observed model, storage, and compute cost
  shall be measurable.
- **NFR-023:** The complete judged deployment shall remain reproducible,
  observable, and available through the required judging period.

## 8. Conceptual information model

This section defines product concepts, not a database schema.

| Concept | Purpose |
| --- | --- |
| Workspace | Authorized boundary containing users, policies, sources, and documents |
| Logical document | Stable identity for a document independent of filename or location |
| File instance | A specific local or cloud copy with its own path and lifecycle |
| Document version | A distinguishable content revision |
| Classification result | Versioned analytical result with confidence, evidence, and provenance |
| Relationship | Explainable connection between two logical documents |
| Proposal | Agent-recommended classification, name, destination, or action |
| Batch | Bounded group of documents processed and reviewed together |
| Operation | Intended and actual copy, move, rename, restore, or folder action |
| Checkpoint | Durable progress marker used to resume safely |
| Review decision | Human approval, rejection, correction, or escalation |
| Agent run | Traceable analytical or operational execution |
| Audit event | Append-only record of a material state change |

## 9. Product success measures

The MVP succeeds only if it demonstrates all of the following with current
evidence:

- a representative 300-document corpus completes the approved end-to-end flow;
- a user can prioritize uncertain documents and inspect explanations;
- interrupted processing resumes without repeating completed work;
- individual and batch restores preserve history and avoid overwrites;
- project managers can attribute every material operation;
- classification and relationship quality meet the approved evaluation gates;
- the 10,000-file discovery test remains responsive and preserves state;
- the cloud application visibly uses the same real agents and CockroachDB
  memory as the product workflow;
- no critical security, integrity, accessibility, or competition gate is open.

## 10. Assumptions requiring later architecture decisions

The following are deliberately not decided by this document:

- the embedding model, vector dimension, and distance metric;
- which extraction steps run locally or in AWS;
- the precise cloud compute service;
- the division between application transactions, database functions, and
  stewardship-agent tools;
- the web framework and desktop packaging method;
- confidence calibration algorithm and final thresholds;
- document retention duration;
- the exact approval policy for each action class.

Each choice requires an explained architecture proposal and explicit approval.

The primary Large Language Model is approved by
[`ADR-0001`](../architecture/decisions/0001-amazon-bedrock-primary-model.md).
The physical CockroachDB schema and the relational representation of proposed
and canonical facts are approved by
[`ADR-0002`](../architecture/decisions/0002-cockroachdb-physical-data-model.md).
